# Problem and Experiment Patterns

Use only the patterns that help with the user's stated situation. Recommend a path; do not turn this map into a questionnaire.

## First-Conversation Budget

Before producing durable instructions, understand enough to identify:

- the work the user wants to improve;
- the difficulty they notice;
- its practical effect;
- the environment they are using;
- whether they want a quick experiment or a more durable setup.

These are information needs, not five mandatory questions. Infer what the user has already supplied. For lost history, prefer one longer account over serial prompts.

Do not make accessible presentation depend on this discovery. Apply readable structure immediately; use discovery only to refine the result or create durable personal instructions.

## Universal Delivery Pattern

For any substantive explanation or multi-stage instruction:

1. answer the immediate question;
2. make a quick route available;
3. provide a guided route when execution benefits from stages;
4. provide an uninterrupted complete route for users who want the whole model;
5. keep optional technical depth reachable without placing it in the main route;
6. offer a resumable record when work may extend beyond chat.

Expose the routes once. Do not make the user proceed through repeated permission questions or justify why they want a particular depth.

Treat configuration, process, and other multi-step how-to requests as substantive even when the user's question is short. Put the route offer after the immediate answer and keep it to one unobtrusive sentence.

## Common Problems and Candidate Patterns

| Problem described | Patterns worth demonstrating |
| --- | --- |
| Any substantive explanation or multi-stage instruction | Immediate answer; quick route; guided route; uninterrupted complete route; optional technical depth; resumable record when relevant |
| Main point disappears | Answer first; short orientation; proposition-led paragraphs; bounded detail |
| Too much text to process quickly | Chunking; headings; summaries; visual guides; layered detail |
| Long instructions become tiring | Destination first; short phases; one actionable step; resumable checkpoint |
| Step-by-step becomes tedious | Give an overview and let the user move between guided and complete views |
| Bullets feel unattractive | Compare prose, bounded bullets, key–value pairs, or a table on one small example |
| Conversation wanders | Record the new thread; restate the current focus; preserve a return point |
| Decisions disappear | Record the decision and reason; keep dated history; derive a current view |
| Earlier work is hard to find | Durable Markdown; descriptive titles; linked instructions; retrieval cues |
| User repeats context | Resumable summary; stable reference; approved chatbot memory as fallback |
| Output is hard to share | Portable Markdown; reading HTML; later privacy-checked sharing copy |

## Information-Design Principles

Teach only what is relevant:

- **Space:** separation reduces visual competition.
- **Chunks:** bounded units support scanning and resumption.
- **Guides:** headings, emphasis, summaries, and navigation show where to look.
- **Information structure:** put the important proposition before supporting context.
- **Simple language:** prefer direct clauses and useful verbs without deleting necessary concepts.
- **Scanning versus skimming:** scanning locates a target; skimming builds a quick model of the whole.
- **Outline:** reveal relationships and order, not merely a decorative heading hierarchy.
- **Propositions:** make the claim or action explicit; do not bury it inside framing language.
- **Parallel depth:** provide quick, guided, complete, and technical routes without forcing the user through them sequentially.

## Early-Example Method

1. Select the single principle most likely to help.
2. Explain its intended effect in one or two sentences.
3. Show two compact versions of the same generic content.
4. Ask the user to find, explain, or act on something—not only choose which version looks nicer.
5. Offer to repeat the experiment with the user's content.
6. Record aesthetic response, task usefulness, and context separately.
7. Treat the result as **Trying** until it survives real use.

Use a third variant only when it tests a materially different structure. Stop before the comparison becomes another large information load.

## Problem-Led Language

Mention accessibility and neurodivergence as possible contexts, not as the organising frame. Prefer concrete descriptions such as attention, rapid processing of large amounts of text, difficulty with long instruction lists, resuming interrupted work, or finding earlier decisions. Never infer a diagnosis or fixed style from a label.

## Pacing Failure Signals

Stop gathering information and demonstrate a result when:

- the user repeats or circles the same concern;
- answers become shorter or impatient;
- the conversation itself starts wandering;
- enough evidence exists for a reversible experiment;
- the user asks to see what the advice would look like.
