# Sources, screenshots and evidence

## Sources that match the visual

Prefer the source that actually establishes the claim: paper, benchmark provider, proof artefact, official product documentation, or a clearly identified personal project record. A homepage is sufficient for product identity, not a quantitative performance claim.

For paper references, verify author, title, year, DOI/arXiv and version. Keep publication/announcement dates separate from discovery dates, model release dates and evaluation dates. A first version can retain its original title while the current arXiv page is renamed; pin the cited version rather than silently mixing metadata.

When graphs compare measurements, retain the source snapshot and exact values. Do not join incompatible benchmark versions or tiers into one trend. Label inference settings, tools, denominators and uncertainty when they affect interpretation. Standard errors are not confidence intervals. Retrospective scores plotted by model release date need that meaning stated explicitly, including a benchmark-release marker when useful.

A proof collection can contain distinct kinds of achievement: competition proof, new algorithm, novel bound, known-proof formalisation, public research manuscript, or announcement whose artefacts remain held. Keep the category and public evidence visible. Reading a repository is not replaying Lean verification; do not describe it as such. A provider's claim and an independently checked result need different attribution.

## Capture real tool states

Use the user-authorised surface. Public-page capture is a useful default when private workspace access is unnecessary; a request to show a signed-in tool can require clarification of the intended workspace. Do not infer permission to expose private research from a request for product screenshots.

Capture with the browser tool or a bundled headless browser, using the current environment instructions. Do not launch or automate the user's real browser profile merely to get a screenshot. Prefer a relevant public interface; otherwise use an official product/research page and label what it is. Repository pages can illustrate code-first tools when labelled as repositories.

Per capture, retain:

- Requested/final URL and product name.
- UTC capture time, viewport and page kind.
- File path, format and SHA-256 hash.
- Access/capture outcome; reason and attempted public fallbacks when unavailable.
- Original-versus-derived preview relationship if resized or compressed.

Inspect the images, for example through a labelled contact sheet. A successful HTTP response can still show a challenge, login wall, blank loading state or a cookie panel obscuring the product. Allow normal loading or try a small number of relevant public alternatives. If no usable page is accessible, record unavailable rather than fabricating an interface or counting the blocked screen as a product capture.

Show image, source URL, capture date and page kind together in a screenshot widget. Its assertions concern the public page at capture time, not a hands-on evaluation of every advertised feature. Screenshots are evidence of interface appearance, not proof of product performance.
