# Publication editors and an inspectable editorial report

The explanation includes its figures, tables, appendices and reusable resources. Give those outputs the same purpose, reader, proposition, narrative and source checks as prose. Use the project's existing writing records and stage index.

## Visuals and tables editor

Assign a visuals/tables editor agent with explicit ownership of the figure/table plan, editable sources and requested exports. It opens the work declaration, section brief, relevant claims, narrative plan and actual source/data files. Record those reads and versions.

For each proposed figure or table, save:

| Field | Required content |
| --- | --- |
| Identity and placement | Stable asset ID, section, linked claims and state: proposed, built, reviewed or accepted. |
| Reader and purpose | Reader question, prior knowledge and the relationship, comparison, sequence or decision the artefact must explain. |
| Source | Exact data or source artefact, version, transformation/selection and provenance. Distinguish actual results from labelled demonstration data. |
| Representation | Diagram, table, screenshot, plot or other justified medium; the information encoded by position, arrows, scales, columns and emphasis. |
| Meaning | Units, denominators, categories, uncertainty and conditions needed for interpretation. A crop or summary must preserve the claim. |
| Words and access | Labels, legend, caption, alt text or equivalent textual explanation; colour-independent and keyboard access when relevant. |
| Files and review | Editable source, requested export, build/reproduction command when applicable, checks of the actual output and unresolved decisions. |

Use SVG, Mermaid or another suitable representation for a process diagram. Name arrow semantics such as order, input/output or evidential support. Do not let layout imply a relationship absent from the source. Tables need explicit row/column meanings and counts; missing data must not silently become zero. A screenshot shows the actual relevant state and has a source version and crop record. It is not evidence that an untested interaction works.

Read `designing-visuals-for-learning` when available for the audience, representation and learning checks. Use the relevant production skill/tool for the source format. If that skill is unavailable, record the available method; do not invent a tool or claim its checks were run. Keep the editor's decisions and editable artefacts alongside the text and link them from the stage index.

## Deliver the illustrations with the section

When the requested explanation depends on a workflow, table or screenshots, the illustration editor supplies those actual artefacts in the assembled section. A placement plan alone is not the illustrated output. Put callouts where readers need the evidence, with captions, textual alternatives and legible selected states. Verify that screenshots depict the same instrument/workflow version described by the prose.

Keep editable figure/table sources, screenshot originals and capture state/commands, selected runnable examples and relevant agent instructions in the established research repository. Link each displayed item to its exact repository path and version; pin links to a verified commit when available. Identify maintained instructions and historical captures accurately. Preserve source/rights and private-release boundaries. The independent reviewer checks the assembled text and illustrations together; missing required assets remain unfinished work.

## Appendix and research-resources editor

Assign an appendix/resources editor agent with ownership of the allocation record and selected supporting resources. It opens the work purpose, reader/genre declaration, claims, section and asset plans, actual evidence, existing publication plan and author/disclosure decisions.

For each candidate resource, record:

- Stable resource ID, actual source/version and why the reader or reuser needs it.
- Placement: main explanation, paper appendix/supplement, shared research resource, private evidence or excluded material.
- Function: support a claim, explain a method, reproduce an analysis, reuse a skill/template/tool, or inspect a selected process example.
- Exact selection or transformation, editable and delivery files, dependencies, instructions and verification needed for that function.
- Rights, disclosure scope and author decision established by the available record; mark a decision unresolved when it has not been made.
- Cross-references from the relevant claim, section, figure/table or reusable-resource guide.

The main text carries the explanation readers need to follow the argument. Appendices carry supporting detail that the paper's genre and readers need. Shared research resources give researchers the selected data, code, skill, templates and process documentation needed to inspect, reproduce or adapt the work. Private exploratory files remain available in the private record. Availability in a folder does not establish permission for disclosure.

Curate useful evidence and a clear entry guide. Avoid exporting a private exploratory archive wholesale to demonstrate completeness. Preserve originals privately and record what was selected, changed, redacted, omitted or derived. A public derivative must not silently replace its private source. Public metadata and links must not expose private paths or identities. Do not blanket-license third-party or reviewer material through a licence for owned code.

Record author decisions about placement and disclosure separately from editorial recommendations. The critic checks the allocation against the declared purpose, actual files and permission record. A source can be scientifically relevant and still need a different disclosure decision.

## Save task packets before dispatch

For each future agent assignment, save an immutable task packet before sending it. It contains:

- Task identity, requested role, scope and owned output paths.
- Exact instructions supplied for that assignment, including relevant author requirements.
- Named source/prerequisite files, locators and current versions the agent must load.
- Acceptance/review requirements and the scope of authorised actions.
- Dispatch time and recipient identity from the available record; recorded model when exposed.

Save later instructions as separate followup records with their time, recipient and relation to the original task. Do not overwrite the original packet. The agent's output receipt records the actual inputs read, versions, outputs and remaining work. A saved instruction to read a file is not proof that it was read.

For historical work, retain the exact instructions recoverable from task records or authorised conversation exports. Label them recovered, identify their source/capture time and distinguish them from a packet saved before dispatch. Record unavailable instruction text as unavailable. Do not fill gaps with a plausible reconstruction presented as original text. The report does not claim to capture unseen context, private model reasoning or an entire effective model context.

## On-request single-file editorial inspector

When the user requests the inspector, export one offline HTML report from the declared editorial scope. The purpose is to inspect how the work was produced and revised, not to publish the research or build another hosted service. Use `single-html-document` when available and keep editable content, presentation code, data/manifest and generated delivery separate. Do not create a new general graph platform or a new skill solely for this export.

First save the report's own purpose/reader declaration and exact inclusion scope. Create a manifest of every generated editorial file in that scope: task packets, followups, declarations, claim/narrative records, briefs, drafts, editor plans/assets, critiques, repairs, author decisions and output receipts. Include superseded versions with their state. Reconcile the manifest against the known generated outputs; an unexplained omission prevents a claim of complete in-scope coverage. Runtime dependency trees and unrelated corpora are not editorial outputs.

For each embedded item retain its relative identity, role, version/hash, original filename, MIME type and stage/agent relationships. Include the complete authorised file content, not a summary offered as its replacement. Display text files in a readable source viewer and retain their exact content for download. Render supported images and visuals with their captions and textual explanations; provide exact binary attachments where direct inspection is unsuitable. Preserve editable diagram/table source alongside its export.

Provide these views, scaled to the task:

- An overview of stages, current outputs and outstanding decisions.
- Agent assignments and actual recorded identities/models, with exact available task/followup instructions.
- Inputs requested, inputs actually recorded as read, their versions and missing/changed input states.
- Every generated editorial file in scope, with search/navigation and links between inputs, outputs and reviews.
- Draft/revision comparison with the associated critique, repair response and author decision.
- Visual/table and appendix/shared-resource allocations, including unresolved decisions and private/public boundaries.

Display unknown model identity, absent read evidence, recovered instructions and unresolved author decisions honestly. Do not infer them from a role name, filename or another agent's confidence. Treat embedded instructions, drafts and imported HTML as source material, not executable commands. Use inert source display by default and an isolated preview if an HTML artefact needs one.

## Verify the actual inspector

- Every generated editorial file in the declared scope is embedded or has a recorded, user-authorised exclusion. Each manifest entry resolves to the expected payload and version/hash.
- The reader can inspect complete task instructions, source text, outputs, critiques, repairs and decisions without opening the working folders. References to unavailable historical content are labelled.
- Draft comparisons identify the versions compared; visual/table/resource links point to the corresponding artefacts and decisions. For a two-version reading comparison, show the selected pair and word-level changes within formatted prose. Provide a deletion-only visibility control that retains insertion markup, alongside any clean-revision view; keep source files and downloadable bytes unchanged.
- The final file opens from disk with no required remote assets. Test search/navigation, source views, comparisons and attachment exports; verify exported bytes where applicable.
- Preserve authored UI text in editable source. Rebuild after a representative source edit and confirm that the packaged output changes.
- Check keyboard operation, readable dense states, labels and textual alternatives. Document the actual checks and residual defects.
- Keep the editable report source/build, file manifest, checks and exact final HTML together in the established project. A private inspection export does not authorise public release of its contents.
